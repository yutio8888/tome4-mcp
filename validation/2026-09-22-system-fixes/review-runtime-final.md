### RUNTIME-REV-01 — P2 — public MCP DTOs accept and emit schema-invalid v4 scalars

- Location: `server/src/tome_mcp/server.py:477`, SHA-256 `283eb5bf1678669d97fe162d1aa7b279c47b84651a21f3d6f542e52491138b56`; normative `protocol/v4/common.schema.json:16`, SHA-256 `9b6361382ef5c37c37109deebeb1b1407fb4e154c8d62255f8fe16fb5d4b634e`.
- Trigger: call actual MCP tools with a value whose Pydantic DTO and corresponding v4 wire type disagree. Independently reproduced invalid-but-emitted cases include revision/event upper/lower violations, an empty `use_talent.target_id`, control characters in shared ids/cursors/answer ids, UTF-8 byte overflow, an empty policy hash, and a command sequence above `x-max-sequence`. The inverse also occurs: 129 printable ASCII characters are valid under the 256-byte Session/Entity/Talent types but the MCP boundary rejects them for session id, inspect id, and talent id because several Python fields cap code points at 128.
- Expected: the public tool schema and local validation enforce the corresponding v4 bounds/shapes and reject invalid input before TCP. In particular `Revision` is `1..9007199254740991`, `EventCursor` has the same upper bound, supplied entity ids are non-empty/control-free, and cursors are printable ASCII.
- Actual: invalid examples are accepted and emitted (some custom `x-*` limits require the generated Runtime validator rather than a stock JSON Schema validator), while valid 129-byte examples are rejected before wire. The advertised `tome.act` revision minimum is also `0`. Runtime's generated schema still prevents mutation when a real game receives the invalid examples, but the public MCP boundary violates its own wire contract and reports the error at the wrong layer. Reproduction: `review-runtime/RUNTIME-REV-01-repro.md`.
- Oracle gap: `server/tests/test_public_contract.py:58-94` validates only one sampled valid value for each tool, so the test named “all tools emit schema-valid requests” does not exercise invalid numeric/string boundaries.
- Direction: define/reuse public DTO validators for the shared v4 scalar types (including both bounds and character/byte constraints), then add actual MCP negative calls at lower/upper/string boundaries and assert none reaches `FakeGame`. At minimum cover all occurrences of Revision/EventCursor and the identifier/cursor/action-id types; do not patch only `act`'s lower bound.
- Amendment disposition: `79cf8c4b3389161127a5445f3e36dd005bbad898` was a correct revision-only partial fix. Follow-up `2e2acc721906767c7773a73ad95eebb4b2f1e54a` completes the public scalar alignment: shared identifier/option/cursor byte and character rules, command sequence, Revision/EventCursor/Coordinate bounds, nested action/answer IDs, and distinct inline opaque/dismiss fields are derived from the actual v4 shapes without retaining the erroneous 128-character cap. Its matrix extends JSON Schema validation for the normative `x-max-utf8-bytes` and `x-max-sequence` keywords and exercises 1,625 actual MCP calls, including positive multi-byte boundaries and inline exceptions. Independent exact-pin runs pass all 47 Python tests plus the protocol generator; direct rerun confirms valid 129-byte session/inspect/talent IDs each reach TCP once, while every previously reproduced invalid case is locally rejected with zero TCP requests. RUNTIME-REV-01 is resolved at source/server layer.
- Final recheck: final test-only follow-up `4bc0bb206c2d1299a284efdf1e7e8a7ee2d0f7b6` adds both sides of the historical 128/129-byte boundary without changing production bytes. I independently reran the final pin: all 47 Python tests pass and the scalar matrix executes 1,787 actual MCP calls. `server.py` SHA-256 is `36f251558046efa171eb1e63a6796a04c21e76fd07c5ba170502591ace91dec9`, and the separately shipped server archive matches that pinned source. ### RUNTIME-REV-03 — P2 — loading two legacy policy versions loses the original draft bytes

- Locations: `overload/mod/auto_combat/PolicyStore.lua:80-103`, SHA-256 `820a9f9f5158e814cf19c2a88e3f7b81cf0eb302a889e4eed4e78c1b22ba7b39`; load order at `overload/mod/auto_combat/AutoCombatService.lua:869-874`.
- Trigger: load a format-2 save containing both a legacy draft and a legacy approved policy whose `mode.on_low_hp` is `emergency_only` and which both omit `on_emergency_unavailable`.
- Expected: per POLICY-02 and design section 5.4, the migrated approved policy becomes the new draft requiring reapproval, while the pre-existing user draft is preserved under `migration.previous_draft` and the original approval under `migration.original_approved`.
- Actual: restoring the draft first migrates it and temporarily archives `original_draft`; restoring the approved version replaces the migration record, copies the already-migrated draft into `previous_draft`, and drops `original_draft`. Independent production-module reproduction showed `draft_exact_preserved=false`, `previous_draft.mode.on_emergency_unavailable=release_control`, `approved_exact_preserved=true`, and `original_draft_archive=nil`.
- Oracle gap: `tests/test_auto_combat_sysfix.lua:348-354` uses a draft that already has the new field and asserts only its id, so it cannot detect loss of the original legacy draft representation.
- Direction: preserve the pre-migration draft (or carry forward its `original_draft`) when a later approved migration replaces the migration ledger; regression should compare the full canonical original draft and approval bytes after load/save/reload, including the both-legacy case.
- Interim amendment disposition: `ae8baf8df1122b67b9157bae9e4561e1e789ee9c` keeps a private `draft_source` snapshot synchronized on restore/set/clear and uses it for `previous_draft` when a legacy approval supersedes the live draft. Independent exact-pin runs pass sysfix 680, policy-bytes 209, and Service 192 checks; a direct production-module reproduction reports original draft and approval bytes preserved both before and after save/reload while only the live replacement gains `release_control`. At that interim point source/offline disposition was satisfactory but rebuilt-package/native evidence was still pending.
- Final recheck: both final policy native runs exercise the real in-engine Service/Store dataflow for three consecutive migration/save-data restore rounds. Each round preserves the exact original draft bytes as `previous_draft`, the exact original approval bytes as `original_approved`, leaves the migrated live policy unapproved, and rejects activation. These rows are not mislabeled as filesystem reload; the separate core source/dist suites supply the real Ctrl+S/new-process persistence boundary. RUNTIME-REV-03 is `CLOSED`.

### RUNTIME-REV-04 — P2 — policy import silently accepts a missing or non-string integrity hash

- Location: `overload/mod/auto_combat/PolicyIO.lua:27-45`, SHA-256 `a9b0bb508dedc5d5965563f5d095c9b07dca3382f524f10e452df4445e9cbb74`.
- Trigger: export a valid policy envelope, then delete `hash` or replace it with a number before calling the production `PolicyIO.import`/`Service.import` route.
- Expected: the documented envelope carries a content hash, and POLICY-02 requires import to verify the original envelope hash before semantic migration; a missing/malformed hash cannot satisfy that requirement.
- Actual: the comparison runs only when `type(data.hash)=='string'`; both missing and numeric hashes bypass verification and import successfully. Independent production-module reproduction returned `missing_hash_accepted=true` and `numeric_hash_accepted=true`.
- Consequence: a hand-edited/stale policy can be accepted without the integrity check promised by the envelope and migration contract. This is especially material now that migration reports `original_hash`: that value is merely recomputed when the caller supplied no valid authority.
- Oracle gap: tests cover a mismatching string hash, but not hash presence/type on an otherwise-valid policy.
- Direction: require a correctly typed hash before policy preparation/migration, return a typed envelope error when absent/malformed, and regress missing, null, numeric, empty, mismatching, and valid hashes while retaining the rule that semantic invalidity is reported before a mismatch only after the envelope itself is structurally valid.
- Interim amendment disposition: `dca36dc1ac1013e40710d8449cda41931af259b8` makes a non-empty string hash mandatory before policy preparation/migration and returns registered `invalid_document` details for malformed envelope structure. Tests cover missing/null/number/empty/boolean/object values with invalid and valid policy bodies, Codec no-work assertions, mismatch/valid/current/legacy hash paths, migrated-hash rejection, and unchanged Service store/control state. Independent exact-pin runs pass IO 110 and sysfix 680 checks; direct production calls reject missing/null/numeric/empty hashes and accept a valid exported hash. At that interim point source/offline disposition was satisfactory but rebuilt-package/native evidence was still pending.
- Final recheck: source and dist policy runs both reject missing/null/numeric/empty hashes with `invalid_document`, reject mismatching and migrated hashes with `hash_mismatch`, accept the valid current/original legacy hash cases, and assert the Service store remains unchanged on every rejection. RUNTIME-REV-04 is `CLOSED`.
- Assigned verdict impact: historical SYS-02 `FAIL` at the finding pin is preserved; final-pin verdict is `PASS`.
